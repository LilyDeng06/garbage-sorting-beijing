# 垃圾分类与投放指导系统：阶段成果及开发计划

## 1. 当前成果

已完成 EfficientNet-B0 的 15 个 epoch 迁移学习：前 3 轮冻结主干训练分类头，后 12 轮整体微调。

按验证集选择，第 13 轮在本次全部 15 轮中，细类准确率和四大类准确率均最高，可以作为第一版基线。

| 权重 | 265 类验证准确率 | 四大类验证准确率 |
|---|---:|---:|
| epoch_003.pt | 76.53% | 93.99% |
| **epoch_013.pt** | **83.67%** | **96.05%** |
| epoch_015.pt | 83.52% | 95.98% |

第 13 轮训练准确率为 93.83%。训练与验证仍有差距，后期验证指标有波动，不能用更高的训练准确率代替泛化评估。第 13 轮相较第 3 轮，细类提升约 7.14 个百分点，四大类提升约 2.06 个百分点。

这些是同一官方验证划分上的结果，不是独立实拍测试结果，也不是最终投放建议正确率。尚未完成跨划分近重复图片审计、逐类召回率和混淆矩阵分析。

## 2. 数据集具体信息

- 名称：**Garbage265 中文生活垃圾分类数据集**。
- 发布账号/标识：`tany0699/garbage265`。
- 页面：https://www.modelscope.cn/datasets/tany0699/garbage265
- 官方说明：约 13 GB、265 个细类，包含厨余垃圾、可回收物、有害垃圾、其他垃圾。
- 本次实际 CSV 与落盘核验：train **132,673** 张，val **14,612** 张，总计 **147,285** 张。官方说明中的数量与实际索引不同，对外报告本次实际使用数量。
- 每张图有一个类别标签，并不保证画面只有一个物体；没有目标框或分割标注。
- `train.csv` / `val.csv` 的字段为 `image:FILE,category`；category 为从 0 开始的编号，对应 `classname.txt` 行序，不能重排序类别表。
- `classname.txt` 类名形如“厨余垃圾-八宝粥”；“其它垃圾”和“其他垃圾”仅在大类映射时统一，原始细类编号保持不变。
- 数据来源为网络图片整理。数据卡声明 Apache License 2.0；交接应保留来源与数据卡，不能把此声明理解为已逐张核验原始图片权利。

服务器索引目录：`/data/users/luzihan/datasets/garbage265`。

图片缓存目录：`/data/users/luzihan/datasets/garbage265_cache`，实际图片在其中 `data_files/extracted/<哈希>/train` 或 `val` 下。训练脚本自动寻找，无需写死哈希、复制图片或重新划分训练集。

## 3. 网络和训练设置

- 模型：torchvision EfficientNet-B0，ImageNet-1K 预训练，分类头替换为 265 类。
- 输入：RGB、224×224。
- 训练增强：随机裁剪（scale 0.75–1.0）、水平翻转、轻度颜色扰动。
- 验证/推理：官方 `EfficientNet_B0_Weights.DEFAULT.transforms()`，短边缩放到 256，中心裁剪 224，ImageNet 均值与标准差归一化；推理脚本还执行 EXIF 方向校正。
- 优化器：AdamW，weight_decay=1e-4；分类头预热 lr=1e-3，微调阶段主干和分类头均为 1e-4。
- batch_size=64，workers=4；交叉熵损失。
- 训练环境：实验室 A800 80GB，Python 3.11，PyTorch 2.13.0+cu130，torchvision 0.28.0+cu130，Conda 环境 qwen（据服务器输出）。
- 四大类指标定义：先取 265 类 argmax，再将这个类别映射成大类；不是把同一大类的 softmax 分数相加再决策。

## 5. 推理运行方法

使用有匹配版本 PyTorch/torchvision 的 Python 环境，另需 Pillow。已有 GPU 训练环境不必重复安装；新电脑应按操作系统选择对应的 CPU 或 GPU PyTorch 安装包。

将权重、预测脚本和测试图片放入同一工作目录，执行：

```bash
python predict_garbage265.py --checkpoint epoch_013.pt --image example.jpg
```

GPU 推理可追加 `--device cuda:0`。返回字段：`prediction.class_id`、`label`、`item`、`waste_category`、`score`，以及 `topk` 候选列表。

注意：score 是未校准的 softmax 分数，不等于实际正确概率。预测脚本每次调用会加载模型，适合先验证；后端服务应在启动时加载一次模型并复用。

## 6. 功能边界与模块分工

当前已实现：单张图片的具体物品识别和数据集大类映射。

当前未实现：多物体定位、污染/残液状态识别、城市规则适配、未知物拒识、可靠的不确定性阈值、网页和 API。

| 前端 | 图片上传、结果和候选项展示、用户纠正入口 | 能调用统一预测接口，提示单件主体拍摄 |

## 7. 多目标识别：框选效果与实现路线

当前网络每张图输出一组分类分数，不输出目标框。下一阶段希望在一张图中分别框出多个垃圾，并为每个框给出物品名称和大类。

下面是拟实现的结果形式，**仅为布局示意，不是数据集原图、人工标注真值或模型实测输出**：

```text
┌──────────────────── 一张照片 ────────────────────┐
│  ┌──────────────┐           ┌──────────────┐     │
│  │   饮料瓶     │           │    果皮      │     │
│  │              │           │              │     │
│  └──────────────┘           └──────────────┘     │
│   物品：饮料瓶                 物品：果皮         │
│   大类：可回收物               大类：厨余垃圾     │
└─────────────────────────────────────────────────┘
```

人工标注时，每个框需包含边界坐标和类别；推理时显示预测框、类别和模型分数。实际投放还需结合物品状态及当地规则。

实施步骤：

1. 从高频生活垃圾中选择一批明确类别，不一开始覆盖全部 265 类。
2. 评估 UrbanWaste、TACO 等带框或分割标注的数据，并补充目标使用场景的自采照片；先核对类别和使用条件。
3. 标注同图多物品、遮挡和复杂背景，按拍摄场景划分训练与评估数据。
4. 训练检测模型，逐目标输出框和类别。也可试验“检测定位后裁剪，再交给当前分类器”的两阶段方案，但需要验证裁剪图与原分类数据的差异。
5. 用检测 mAP、漏检率、逐目标分类效果和响应时间评估，不能沿用当前整图 96.05% 来描述检测性能。

## 8. 语音输入与投放查询

语音功能拟支持“这个饮料瓶怎么扔”“杯子里还有饮料，要怎么处理”等查询。实现路线为：

**语音 → 语音转文字 → 提取物品与状态 → 匹配投放规则 → 展示答案，可选语音播报。**

语音转写和意图理解需要独立模块，Garbage265 不含语音训练数据。初版可接入现成语音识别能力，使用明确的物品名称词表与规则检索；后续再评估是否需要领域适配。

测试重点包括：物品名转写正确率、口语和同义词理解、最终投放建议正确率、响应时间。含糊表达应追问，例如用户说“这个怎么扔”但未提供图片或物品名时，先获取对象信息。

语音与图像可以结合：先拍照识别，再通过语音补充“里面还有液体”等图片不能可靠判断的信息。语音转写成功并不等于投放建议正确，两个环节需分别评估。

## 9. 系统集成流程

| 输入方式 | 识别与理解 | 共同输出 |
|---|---|---|
| 单件垃圾照片 | 现有 265 类分类器 | 物品、垃圾大类、处理建议 |
| 多件垃圾照片 | 待开发的检测模块，逐目标识别 | 各个框对应的物品和建议 |
| 语音描述 | 待接入的语音识别和物品/状态提取 | 对所描述物品的投放指导 |

三个入口共享同一套地区投放规则。第一版先选定一个地区，规则保存来源与更新时间；遇到不确定类别、不可见状态或规则缺失时，提供补拍、确认或人工查询入口。模型分数未校准，不能直接当作正确概率。

## 10. 实施计划与验收

| 模块 | 近期任务 | 验收重点 |
|---|---|---|
| 模型与评估 | 验证第 13 轮权重、整理混淆矩阵和逐类召回率 | 实拍效果与有害垃圾漏判情况 |
| 前后端 | 图片上传、模型常驻服务、结果与候选项展示 | 完整跑通一次识别流程 |
| 语音交互 | 录音、转写、物品和状态理解、可选播报 | 口语查询能得到有依据的答案 |
| 多目标识别 | 选择类别、准备带框数据、训练与展示预测框 | 多物品逐个识别，统计漏检 |
| 投放规则 | 选定地区、整理规则及处理步骤 | 来源可追溯，能更新与纠错 |

建议先完成单图演示和独立实拍诊断，再并行扩展语音、多目标。创新价值通过“是否减少错误投放、是否更方便用户表达、是否处理真实复杂场景”来验证，而非仅以更换网络体现。
